# Portfolio — Qalib Qurbanov

A modern, dark-themed one-page portfolio. React 19 + TypeScript + Vite + Tailwind CSS v4, built with a feature-based architecture and deployed to GitHub Pages via GitHub Actions.

## What's in this folder

The repo root only holds things that git/GitHub/Claude Code require to sit
exactly there. The entire app — everything npm and Vite touch — lives one
level down, in **`website/`**.

| Item | What it is | Do you touch it? |
| --- | --- | --- |
| **`website/`** | The whole app: source code, config, dependencies | **Yes — this is the project.** |
| `scripts/` | `run-app.bat` — double-click to start the dev server | Only to run it |
| `README.md` | This file | For reference |
| `.gitignore` | Tells git which generated folders to ignore | Rarely |
| `.github/` | The GitHub Actions workflow that builds & deploys on push | Rarely |
| `.claude/` | Claude Code's own project settings for this repo | Never (not app code) |
| `.git/` | git's internal database — this *is* the repository | Never by hand |

Inside `website/`:

| Item | What it is | Do you touch it? |
| --- | --- | --- |
| **`src/`** | The site's code — components, content, styles | **Yes — this is the project.** |
| **`public/`** | Static files served as-is (favicon, etc.) | Yes, if you add static assets |
| `config/` | Every build tool's own settings file (Vite, PostCSS, tsconfig, oxlint) | Rarely |
| `package.json` / `package-lock.json` | npm's list of dependencies | Rarely — npm edits this for you |
| `tsconfig.json` | A one-line stub pointing at the real configs in `config/`; TypeScript tooling requires this exact filename at its project root | Never |
| `index.html` | Vite's SPA entry point (loads fonts, mounts React) | Rarely |
| `node_modules/` | Downloaded dependencies (huge, disposable) — recreated by `npm install` | Never |
| `dist/` | The production build output — regenerated by `npm run build` | Never |

`node_modules/` and `dist/` are both git-ignored (even nested inside `website/`),
so they never end up on GitHub — they just look like clutter locally because
npm/Vite regenerate them next to your code.

## Architecture

```
website/
  config/         Every build-tool config, grouped out of website/'s own root:
                   vite.config.ts, postcss.config.js, tsconfig.app.json,
                   tsconfig.node.json, .oxlintrc.json
  src/
    app/          App shell that composes the page (App.tsx)
    features/     One folder per page section — hero, about, experience,
                   projects, skills, blog, contact. Each owns its component(s).
    components/
      layout/     Navbar, Footer, LanguageSwitcher — persistent chrome around the page
      ui/         Small reusable primitives (Container, Reveal, SectionHeading, Tag)
      icons/      Hand-rolled brand icons (GitHub/LinkedIn — see note below)
    content/      Typed content, one subfolder per locale (en/, az/, ru/) — see below
    i18n/         Locale state + the useContent()/useLocale() hooks (see below)
    types/        Shared TypeScript interfaces for content
    hooks/        useInView (scroll-reveal), useScrolledPast (navbar backdrop), useTheme (light/dark)
    lib/          Small framework-agnostic helpers (date formatting)
    styles/       Global stylesheet (Tailwind + theme tokens)
```

`website/`'s own root only keeps what npm and Vite genuinely require to live
there: `package.json` (npm), `tsconfig.json` (a tiny stub that just points at
the two real configs in `config/` — TypeScript/editors need *this* file at
`website/`'s root to auto-detect the project), and `index.html` (Vite's SPA entry
point). Everything else that's purely a build-tool's own settings file lives
in `config/`; `npm run dev|build|lint|preview` all point at it already, so
day-to-day commands don't change.

**Why this shape:** sections are independent features that only import shared
`components/ui`, `content`, and `hooks` — they don't reach into each other.
Content is fully separated from presentation and typed, so editing text can't
silently break a component's props. Path imports use the `@/*` alias (see
`config/tsconfig.app.json` / `config/vite.config.ts`) instead of relative
`../../..` chains.

**Scroll-reveal:** `components/ui/Reveal.tsx` wraps content in a small
`IntersectionObserver`-backed hook (`hooks/useInView.ts`) so each section
fades/slides into place the first time it enters the viewport, instead of a
one-shot animation on page load.

**Icons:** `lucide-react` v1 dropped brand/logo icons, so GitHub and LinkedIn
are small inline SVGs in `components/icons/BrandIcons.tsx`; everything else
uses `lucide-react` directly.

## Editing content & languages

The site ships in English, Azerbaijani, and Russian. Content lives under
`src/content/<locale>/` — `en/`, `az/`, `ru/` — each with the same set of
files (`profile.ts`, `about.ts`, `experience.ts`, `projects.ts`, `skills.ts`,
`blog.ts`, `ui.ts`). Edit the file for the language and section you want to
change; component code shouldn't need to touch.

All three locales are typed against the same `Content` interface
(`src/types/content.ts`), so if a translation is missing a field the others
have, it's a **TypeScript build error**, not a silently blank spot on the
page — `npm run build` catches it immediately.

Before publishing, update at least (in all three locale folders):

- `<locale>/profile.ts` — your real email, GitHub, and LinkedIn URLs
- `<locale>/experience.ts`, `<locale>/projects.ts`, `<locale>/blog.ts` — currently placeholder entries

**How language switching works:** `src/i18n/locale.ts` defines the supported
locales and detects the initial one (saved choice in `localStorage`, else the
browser's language, else English). `src/i18n/LocaleProvider.tsx` wraps the
app and holds the current locale; `src/i18n/context.ts` exposes it as two
hooks — `useContent()` (the full translated content tree) and `useLocale()`
(the locale code + a setter, used by `LanguageSwitcher` and for locale-aware
date formatting in `lib/date.ts`). Adding a fourth language means adding a
`src/content/<code>/` folder with the same files and one line in
`contentByLocale` (`src/content/index.ts`) and `SUPPORTED_LOCALES`
(`src/i18n/locale.ts`) — TypeScript will point out anything the new locale
is still missing.

## Local development

All commands run from **`website/`**, not the repo root:

```bash
cd website
npm install
npm run dev      # start the dev server (http://localhost:5173)
npm run lint     # oxlint
npm run build    # type-check (tsc -b) + production build to website/dist/
npm run preview  # preview the production build locally
```

Prefer double-clicking instead of a terminal? `scripts/run-app.bat` `cd`s into
`website/`, installs dependencies (first run only), and starts the dev server.

## Deploying to GitHub Pages

There's no separate "deploy" step or script — a plain `git push` to `main` is
the trigger. A GitHub Actions workflow (`.github/workflows/deploy.yml`) picks
it up automatically and lints, builds, and publishes the site to GitHub Pages.

1. First time only — push this repo to GitHub:

   ```bash
   git remote add origin https://github.com/<your-username>/<your-repo>.git
   git push -u origin main
   ```

2. In the repo, go to **Settings → Pages** and set **Source** to **GitHub Actions**.
3. From then on, whenever you want to publish changes:

   ```bash
   git add -A
   git commit -m "..."
   git push
   ```

4. Watch it build in the **Actions** tab. Once it finishes, the site is live at
   `https://<your-username>.github.io/<your-repo>/`
   (or `https://<your-username>.github.io/` if the repo is named `<your-username>.github.io`).

`website/config/vite.config.ts` uses a relative `base: "./"`, so it works for
either a project site or a user/org root site with no changes. The workflow
(`.github/workflows/deploy.yml`) runs all npm commands with `website` as its
working directory and uploads `website/dist` as the Pages artifact.
